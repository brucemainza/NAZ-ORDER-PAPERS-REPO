1. Overview

The Order Papers system now uses a Retrieval-Augmented Generation (RAG) pipeline to help parliamentary staff detect duplicate, substantially similar, or related questions and motions before they are scheduled. The pipeline is deliberately local-first: embeddings and LLM inference are served by a local Ollama instance, and all vector data stays in the existing PostgreSQL + pgvector database.

The design principle is unchanged: retrieval first, grounded explanation second, human decision last. The LLM never invents procedural facts; it only classifies and summarises the evidence that retrieval found.

What is implemented today
  • 768-dimensional semantic embeddings via Ollama embeddinggemma:300m.
  • Chunk-level indexing with content hashing and model-digest tracking.
  • Hybrid retrieval: PostgreSQL full-text search + pgvector cosine search fused with Reciprocal Rank Fusion.
  • Grounded explanations from Ollama qwen3.5:4b with a strict JSON schema.
  • Asynchronous explanation jobs, idempotent re-indexing, and an audit trail.

Why it stays inside the backend

  • Reuses existing authentication, permissions, audit logging, and database session management.
  • Avoids an extra HTTP service on a CPU-only machine.
  • Slow LLM work is offloaded to the background worker; the search endpoint itself only touches PostgreSQL and Ollama embeddings.

4. Chunk & Vector Storage

Instead of storing one embedding per parliamentary record, the system stores multiple chunks per record in the record_chunks table. This gives better retrieval quality for long motions and keeps embeddings aligned with the chunk of text that produced them.

Key columns on record_chunks

  • record_id — foreign key to the parliamentary record.
  • chunk_index — position within the record.
  • chunk_text — the actual chunked passage, prefixed with the subject.
  • embedding — 768-dimensional pgvector.
  • embedding_model — model name, e.g. embeddinggemma:300m.
  • model_digest — Ollama model digest, so a model update automatically triggers re-indexing.
  • dimension — vector dimension for sanity checks.
  • preprocessing_version — chunking/version tag.
  • content_hash — SHA-256 of chunk_text; unchanged chunks are skipped on re-index.

Lexical source

The parliamentary_records.search_vector column is a PostgreSQL tsvector. Lexical search uses websearch_to_tsquery('english', query) and ts_rank_cd, so exact terms, quoted phrases, and negation work as staff expect.

5. Indexing Pipeline

Indexing is asynchronous and durable. The web request only enqueues work; the actual embedding happens in the background worker.

  1. Trigger — POST /ai/index/{record_id} or POST /ai/reindex enqueues an outbox job.
  2. Deduplication — jobs are keyed by record_id + version + content_hash + model_digest + preprocessing_version, so duplicate or stale requests are collapsed.
  3. Background work — app/jobs/worker.py claims the job, builds the similarity text, and asks Ollama for an embedding.
  4. Chunking — chunk_record() in app/ai/indexing/chunks.py splits text into overlapping chunks of up to AI_CHUNK_MAX_CHARS.
  5. Upsert — ChunkIndexingService.index_record() deletes stale chunks, skips unchanged ones, and inserts only missing chunks.
  6. Coverage — GET /ai/index/coverage reports what percentage of non-draft records are indexed for the current model digest.
Why chunk-level indexing?

Chunk-level embeddings let semantic retrieval find the most relevant passage inside a long motion, not just the record as a whole. The content_hash and model_digest fields make re-indexing safe and idempotent.

6. Hybrid Retrieval Pipeline

The search endpoint runs two retrievers in parallel, then fuses the results.

6.1 Lexical retrieval — app/ai/retrieval/lexical.py

PostgresLexicalRetriever uses websearch_to_tsquery over parliamentary_records.search_vector. Results are ranked by ts_rank_cd and limited to the configured top-k. Filters (session, item_type, status, date, member, ministry, exclude_ids) are applied inside PostgreSQL.

6.2 Semantic retrieval — app/ai/retrieval/semantic.py

PgVectorSemanticRetriever embeds the query via Ollama, then searches record_chunks.embedding using pgvector cosine distance. It filters by:

  • embedding_model, model_digest, dimension, and preprocessing_version — so only compatible chunks are considered.
  • The same visibility and metadata filters as lexical search.

It collapses multiple chunks per record, returning only the best chunk (lowest cosine distance) for each record, then orders records by that distance.

6.3 Rank fusion — app/ai/retrieval/hybrid.py

RRFRankFusion merges the two ranked lists with Reciprocal Rank Fusion:

RRF_score(doc) = Σ 1 / (k + rank_in_list)

# k = 60 by default
lexical_rank = 3  → 1 / (60 + 3) = 0.0159
semantic_rank = 1 → 1 / (60 + 1) = 0.0164
RRF_score       = 0.0323

The fused list is normalised by the maximum possible score and returned as the final ranking. Each result carries its lexical rank, semantic rank, lexical score, cosine similarity, and RRF score.

6.4 Degraded mode

If Ollama embedding generation fails (network error, model not loaded, circuit breaker open), the service catches the error, logs it, and falls back to lexical-only retrieval. The response reports retrieval_mode: "lexical", degraded: true, and a warning message.

7. Grounded Explanation Pipeline

After retrieval, a clerk can request an AI explanation of why the top records are relevant. The explanation is generated by a local LLM and constrained to a strict JSON schema.

7.1 Synchronous endpoint — POST /ai/explain

  1. The router verifies that the supplied evidence records exist and are visible to the user.
  2. AISimilarityService.explain() builds the prompt and calls OllamaExplanationProvider.
  3. The provider sends the prompt to Ollama /api/chat with temperature=0.1 and the JSON schema.
  4. The response is parsed and stored in AIInferenceRun for audit.

7.2 Asynchronous endpoint — POST /ai/explanations

For longer-running explanations, the request queues a generate_explanation background job and returns 202 Accepted. The client polls GET /ai/explanations/{run_id} until the run completes or fails.

7.3 Caching

Explanations are cached by a hash of:

  • Normalised query text.
  • Sorted evidence record IDs.
  • Prompt version.
  • Model digest.

If an identical explanation was already generated, the stored result is returned immediately with cached: true.

7.4 Prompt design

The prompt wraps the query and evidence in <unrusted-query> and <untrusted-evidence> delimiters and instructs the model to treat them as data, not instructions. The expected JSON schema includes:

  • classification — one of exact_duplicate, potential_duplicate, related_matter, no_strong_match.
  • confidence — low, medium, or high.
  • summary, shared_points, important_differences.
  • evidence_assessments — per-record classification and rationale.
  • human_review_required — always true.

9. Access Control & Audit

  • Visibility filters — both lexical and semantic retrievers apply restrict_draft_visibility and restrict_archive_visibility so users only see records they are allowed to see.
  • Evidence verification — the /ai/explain and async explanation endpoints check that every supplied record ID exists and is visible to the requesting user before calling the LLM.
  • Audit logging — every AI search, explanation, index, reindex, and review action writes an audit log entry with the user, action, entity, and IP address.
  • Inference runs — every explanation is stored in AIInferenceRun with the model, model digest, prompt version, latency, result, and error.

10. Resilience & Degraded Modes

FailureBehaviour
Ollama unreachable / model not loadedSearch falls back to lexical-only. Explanation returns a disabled/fallback response. Health endpoint reports the failure.
Embedding dimension mismatchRaises RuntimeError; search degrades to lexical-only with a warning.
LLM returns invalid JSONThe explainer retries with stricter instructions; if it still fails, the result contains an error field and human_review_required: true.
Background job failsWorker retries with exponential backoff up to max_attempts, then moves the job to dead_letter.
Stale indexing requestIf the record was edited after the job was queued, the worker detects the content hash mismatch and skips the stale job.

12. Operational Notes

Running the worker

cd backend
python -m app.jobs.worker

The worker polls every 2 seconds by default. Use --once to process one batch and exit, which is useful in cron-style deployments.

Re-indexing after a model or chunking change

# Queue the first batch of 100 records
curl -X POST http://localhost:8000/ai/reindex \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"limit": 100}'

# The response includes next_cursor; repeat until complete=true.

Checking health

curl http://localhost:8000/ai/health

When to change the preprocessing version

If the chunking strategy changes (for example, AI_CHUNK_MAX_CHARS or AI_CHUNK_OVERLAP_CHARS), increment AI_PREPROCESSING_VERSION. The new version causes the system to treat old chunks as incompatible and re-index them.

Scaling considerations

  • The current design is local-first and CPU-bound. If latency becomes a problem, the first lever is usually adding an HNSW index on record_chunks.embedding.
  • If Ollama becomes a bottleneck, the embedding provider can be swapped for another implementation of the EmbeddingProvider protocol without changing retrieval code.
  • If LLM explanations need to run on a GPU server, only OllamaExplanationProvider and the Ollama base URL need to change.
