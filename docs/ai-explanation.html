1. Scope and guarantees

The AI layer assists parliamentary staff in finding related historical records via hybrid keyword and semantic search. It does not answer a parliamentary question, make a procedural decision, or change a record by itself. As of 2026-09-16 the only AI component in this project is the embeddinggemma:300m embedding model — there is no local-LLM explanation/generation step (see Section 5).

Local

No external model API

Embedding calls go to the configured Ollama service. Parliamentary prompts and text are not sent to a cloud AI provider by this implementation.

Durable

Database-backed work

Indexing and archival work is represented by committed PostgreSQL jobs and outbox events with leases, retries, visible dead letters, and audited recovery.

Optional

AI is not required to run

/readyz does not fail the whole stack when Ollama/the embedding model is unavailable unless AI_REQUIRED=true is explicitly set; search degrades to lexical-only instead.

Important: the response field called score is retained for compatibility and is a ranking score. It is not a calibrated probability. Where available, raw semantic closeness is returned separately as cosine_similarity.

3. Submission, outbox, and indexing path

  1. Normalize identity. Item type, subject, and full text are case-folded, Unicode-normalized, punctuation-normalized, and whitespace-collapsed. The joined identity is stored as an indexed SHA-256 normalized_hash.
  2. Persist domain state and work atomically. The record, audit row, background_jobs item, and matching outbox_events row share the same database transaction. A rollback leaves no orphan job.
  3. Keep submission available. The compatibility whole-record embedding is attempted, but Ollama failure does not reject the submission. The durable embed_record job remains the recovery path.
  4. Claim safely. Workers claim due work with FOR UPDATE SKIP LOCKED, mark a lease, commit the claim, then run the handler. Two workers cannot own the same row concurrently.
  5. Chunk deterministically. Every passage repeats the subject, uses a bounded character budget, overlaps on word boundaries, and receives a stable index and SHA-256 content hash.
  6. Embed in a batch. Missing passages are sent in order to Ollama’s batch endpoint /api/embed. The provider validates result count, order, numeric values, and exact dimension.
  7. Store version identity. Each vector records model name, exact model digest, dimension, preprocessing version, chunk index, and content hash. Unchanged compatible chunks are not embedded again; stale variants are removed.

4. Retrieval, ranking, and degradation

4.1 Exact duplicate lookup

Duplicate detection first queries the indexed normalized_hash for the same item type and excludes Draft records and explicitly excluded IDs. Exact matches receive a deterministic ranking value of 1.0. Only when the exact result set does not fill the requested limit does the compatibility semantic duplicate backend run.

4.2 PostgreSQL lexical retrieval

A stored generated tsvector weights subject as A, full text as B, and member/ministry as C. A GIN index supports websearch_to_tsquery('english', query); ts_rank_cd supplies lexical rank. Visibility, archive permission, session, item type, status, date, member, ministry, excluded IDs, ordering, limit, and offset all execute in PostgreSQL. The corpus is not loaded into Python.

4.3 Chunk-level semantic retrieval

The query is embedded with the active local model. SQL selects only chunks matching the active model name, exact digest, dimension, and preprocessing version. pgvector cosine distance uses the partial HNSW index. PostgreSQL chooses the best passage per parliamentary record; multiple matching chunks therefore collapse into one result with a passage excerpt.

4.4 Reciprocal Rank Fusion

RRF adds 1 / (k + rank) for each list in which a record occurs. The default k is 60. The normalized fused value is exposed as ranking_score and temporarily mirrored to score. The response may also contain lexical_score, lexical_rank, semantic_rank, rrf_score, and cosine_similarity. The UI labels the compatibility value “ranking score.”

4.5 Degraded lexical mode

If query embedding fails or the embedding circuit is open, the service keeps the already-computed PostgreSQL lexical results. It returns retrieval_mode: "lexical", degraded: true, and a human-readable warnings entry. In normal operation, retrieval_mode is hybrid and both ranked lists participate.

Compatibility: clients that only understand results[].score continue to work, while newer clients can correctly distinguish rank fusion from cosine similarity.

5. Grounded explanation flow — removed

Removed 2026-09-16: the project now uses embeddinggemma:300m as its only AI component. The local-LLM (qwen3.5:4b) grounded-explanation feature described in earlier versions of this document — the asynchronous /ai/explanations job, the synchronous /ai/explain compatibility endpoint, the generate_explanation worker job, the ai_inference_runs table, and the "AI Similarity Evidence" panel on the result detail page — has been deleted from the codebase (backend, frontend, and database schema via migration 20260916_0012).

Everything else in this document that depends only on embeddings — hybrid lexical/semantic search (Section 4), the indexing pipeline (Section 3), and the embed_record durable job (Section 6) — is unaffected and remains exactly as described.

6. Durable worker semantics

Job typeHandlerIdempotency / stale-work rule
embed_recordCompatibility record vector plus current chunk indexContent hash prevents an old edit from overwriting new content.
reindex_recordRebuild compatibility/chunk embeddingsRecord/model identity is part of the deduplication key.
index_record_chunksVersioned passage indexingExisting chunk index + hash + model digest + preprocessing version is reused.
archive_recordsArchive records from ended sessionsStatus transition is repeat-safe.

Failures store a bounded error, clear the lease, and schedule exponential backoff (2^attempt_count seconds, capped at one hour). The default maximum is five attempts; exhausted jobs become dead_letter. A five-minute lock expiry allows another worker to reclaim interrupted work. Successful handlers mark linked outbox events published in the same completion transaction.

Each polling cycle upserts worker_heartbeats. Queue depth and dead-letter state are read directly from PostgreSQL by readiness. Run once with python -m app.jobs.worker --once, or continuously with optional --poll-seconds, --batch-size, and --worker-id.

10. Security and data-integrity controls

  • Visibility first: draft ownership and archive permission filters execute before lexical/semantic ranking.
  • Safe not-found: missing and inaccessible evidence are indistinguishable to callers.
  • Permission boundary: indexing, reindexing, and AI review require the established review_submission permission.
  • Review integrity: row locking, idempotency keys, domain vocabulary, relationship validation, database constraints, safe conflict responses, and transactional audit rows protect writes.
  • Private logs: structured logging carries request IDs while redacting bearer tokens, JWT-shaped values, credentials, prompts, queries, and full record text. SQL parameters are hidden.
  • Local deployment: production containers are non-root/read-only where supported, capabilities are dropped, PostgreSQL is not host-published, and default-deny Kubernetes networking is supplied.
Authentication boundary: authentication logic was deliberately not changed by this project. Known PyJWT findings remain documented in docs/operations/security-exceptions.md and are a residual go-live risk that requires a separately authorized remediation.

12. Operating, reindexing, and rollback

Release order

  1. Back up PostgreSQL and confirm encrypted WAL archive freshness.
  2. Build, scan, sign, and digest-pin API/frontend/PostgreSQL/Ollama images.
  3. Run PYTHONPATH=backend python -m scripts.migrate as the one-shot release gate.
  4. Start at least two API and two worker replicas; start Ollama with approved model digests.
  5. Check /livez, /readyz, worker heartbeat, queue depth, and index coverage.

Resumable backfill

PYTHONPATH=backend python -m scripts.reindex_records --batch-size 100
PYTHONPATH=backend python -m scripts.reindex_records --batch-size 100 --after RECORD_UUID
PYTHONPATH=backend python -m app.jobs.worker --batch-size 10

Repeat with the returned next_cursor until complete is true, then wait for pending/retry depth to reach zero and verify GET /ai/index/coverage. If a partial batch fails, resume at the last committed cursor; chunk and job identities make replay safe.

Model change procedure

  1. Record the approved model tag, exact digest, expected dimension, and new preprocessing version if text preparation changes.
  2. Deploy settings without deleting old vectors. New searches exclude incompatible vectors automatically.
  3. Queue the complete resumable backfill and observe throughput, failures, and coverage.
  4. Run retrieval/duplicate evaluation before enabling any threshold-driven automation.
  5. Remove compatibility vectors only in a later migration after rollback and coverage acceptance.

Database recovery objective

Production backup controls target a 15-minute RPO with encrypted WAL archiving and a four-hour RTO with rehearsed point-in-time restore. The complete recovery and validation procedure is in docs/operations/backup-restore.md.

Production-shaped search benchmark

DATABASE_URL=postgresql+psycopg://…/naz_search_benchmark \
PYTHONPATH=backend python -m scripts.benchmark_search \
  --records 100000 --allow-isolated-write-benchmark

The command refuses non-isolated database names, inserts generated records inside one transaction, runs the real PostgreSQL lexical retriever, reports p50/p95/p99/max, fails when p95 exceeds 3,000 ms, and rolls the records back. The local 5 August 2026 acceptance run used eight warm-ups and 40 measured queries over 100,000 records: p50 148.151 ms, p95 160.512 ms, p99/max 168.316 ms. This measures the required lexical continuity path; re-run on target storage and measure the complete hybrid path with the approved Ollama hardware and populated chunk index before site acceptance.

13. Health, diagnostics, and operational signals

Strict readiness

Database connectivity, exact Alembic head, reachable Ollama with both required models, and zero dead-letter jobs decide ready/not-ready. Worker heartbeat remains visible but non-blocking.

Request correlation

A valid inbound X-Request-ID is propagated; otherwise the API creates one. Completion logs and response headers carry the same identifier.

Request logs

Structured request logs retain request IDs, status codes, and durations without requiring a separate monitoring service.

Recommended alerts

  • Core readiness false or schema revision differs from 20260805_0011.
  • Dead-letter depth above zero; retry depth or oldest pending age rising.
  • Worker heartbeat older than WORKER_STALE_SECONDS.
  • AI degraded-search rate or model failure rate above the agreed baseline.
  • Compatible chunk coverage below the release target after a model/preprocessing change.
  • p95 search latency above three seconds on the production-shaped 100,000-record benchmark.
  • Encrypted WAL age above 15 minutes or latest base backup older than 12 hours.

14. Threshold and retrieval evaluation

Thresholds are policy, not model truth. The deterministic evaluator sorts historical clerk decisions by time, derives thresholds on the earlier training period, and measures precision only on the later validation period.

PYTHONPATH=backend python backend/scripts/evaluate_similarity_thresholds.py decisions.csv

The CSV requires decided_at, cosine_similarity, is_duplicate, and automatic_link_correct. The command exits non-zero unless validation reaches 95% duplicate precision and 98% automatic-link precision. Its policy version is derived from a SHA-256 digest of the ordered dataset.

Do not approve production automation from defaults alone. The checked-in thresholds are starting configuration. A representative, time-separated NAZ decision dataset must demonstrate the required precision, and recall plus subgroup error analysis should be reviewed by clerks.

17. Known limits and residual go-live risks

  • Authentication is not hardened here. The frozen PyJWT dependency has documented advisories. Resolve the separate authentication work before unrestricted production exposure.
  • One compatibility path remains for one release: the whole-record vector used by legacy duplicate similarity. Its removal needs a versioned client/data migration.
  • Default thresholds are not evidence: production automation remains blocked until the local historical evaluation meets precision targets.
  • Infrastructure examples need site values: replace example image digests, ingress host, TLS/storage classes, resource sizes, GPU scheduling, external backup storage, and secret integration.
  • Benchmark acceptance is environment-specific: execute the production-shaped 100,000-record test on target PostgreSQL/storage/hardware and record p50/p95/p99, plan, cache state, filter mix, and corpus snapshot.
Operational principle: lexical fallback remains an explicit request-level continuity path, but the application does not report ready while Ollama, required models, schema, PostgreSQL, or the dead-letter queue is unhealthy.
